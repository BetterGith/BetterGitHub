# План BetterGitHub: сначала пользовательские темы

## Цель и границы

Первый приоритет — создавать, называть, редактировать и выбирать собственные темы, оставлять их личными либо публиковать готовый JSON через редактор GitHub. Затем доработать редактор элементов на странице и перетаскивание блоков. Расширение открывает файл в GitHub и передаёт содержимое; пользователь проверяет и подтверждает коммит. Токен и право прямой записи расширению не нужны.

Произвольное перемещение любого элемента GitHub, редактирование текста GitHub и добавление CSS/HTML/JavaScript не входят в план: для них формат и механизм применения не определены.

## Текущее состояние

- Уже работают семь встроенных тем, палитра из шести цветов, фон и эффект; баннер, значок и ссылка установки; порядок пяти блоков боковой панели репозитория через перетаскивание карточек или кнопки ↑/↓ в редакторе. Глобальная личная палитра настраивается на странице параметров. Именованных тем, их библиотеки, импорта и явного светлого/тёмного режима для произвольных цветов пока нет.
- Публичный `.bettergithub.json` читается с `raw.githubusercontent.com` без лимита GitHub API и применяется без записи в репозиторий. Локальные настройки хранятся в `chrome.storage.local` и имеют приоритет над полями JSON.
- Редактор уже скачивает JSON из текущих полей и не сохраняет несохранённые правки при закрытии. Пока нет перетаскивания прямо на странице, карандашей у отдельных элементов и общего режима предпросмотра. `examples/.bettergithub.json` показывает действующий формат.
- Кнопка «Открыть в GitHub» определяет основную ветку и ищет оба варианта имени конфига. Существующий `bettergithub.json` редактируется без создания второго файла. Для профиля новые настройки находятся в `profile` внутри того же JSON, корневые настройки репозитория сохраняются. Автоматическая вставка выполняется один раз; кнопка копирования остаётся запасным вариантом. Коммит пользователь подтверждает в GitHub. Нужна ручная проверка автозаполнения в авторизованных Chromium и Firefox.

## Этап 1. Именованные темы и цветовые режимы

- [ ] Хранить личные темы в `settings.customThemes` по неизменяемому локальному ID. Тема содержит `id`, отображаемое `name`, `mode` (`light`, `dark` или `auto`) и `light`/`dark` версии. Каждая версия содержит `accent`, `base`, `surface`, `text`, `muted`, `border`, необязательные `background` и `effect`. Для `auto` обязательны обе версии; для фиксированного режима — соответствующая одна. ID не использовать как CSS-класс или путь. Имя выводить только текстом.
- [ ] Разделить выбор темы и её содержимое: `{kind: "builtin", id: "midnight"}` либо `{kind: "custom", id: "<local-id>"}` для глобального режима и локальной настройки страницы. Старые `settings.theme`, `settings.global`, `sites` и JSON без новых полей читать без потери настроек. При удалении выбранной темы потребовать выбрать замену.
- [ ] Для опубликованной темы добавлять в `appearance` самодостаточный `customTheme: {name, mode, light?, dark?}` с полной палитрой и фоном; не экспортировать локальный ID, другие темы библиотеки или черновик. Для совместимости с прежним расширением также записывать известный `appearance.theme` (`light` или `midnight`) и плоские цвета запасной версии. Новая версия использует `customTheme`, а при неверной схеме переходит к допустимым прежним полям. Встроенные темы и прежние JSON сохраняют прежнюю семантику.
- [ ] Определять эффективную светлую/тёмную схему GitHub и системы для `auto`, обновлять версию при переключении режима без перезагрузки. `github` оставляет родные цвета GitHub; произвольная тема всегда указывает цветовую схему явно. Учитывать `prefers-reduced-motion` и проверять читаемость текста на поверхности и фоне.
- [ ] В галерее параметров добавить «Мои темы»: создать из встроенной/текущей, назвать, дублировать, редактировать обе версии, удалить и выбрать. Показывать режим и предпросмотр. Правки вести в черновике с отдельными «Применить» и «Отмена».

**Готово, когда:** можно создать две именованные темы, выбрать любую глобально или для страницы, сменить режим GitHub и после перезагрузки увидеть сохранённый результат; прежние настройки выглядят как раньше.

## Этап 2. Импорт, экспорт и публикация темы

- [ ] Импортировать файл только по явному выбору пользователя. Ограничить размер 64 КБ, проверять структуру и разрешённые поля до сохранения, показать название, режим, фон и конфликт имени. При конфликте предложить переименовать или заменить конкретную личную тему. Повреждённый файл не изменяет хранилище.
- [ ] В интерфейсе разделить «Сохранить лично» и «Скачать для публикации». Перед скачиванием собрать JSON из видимого предпросмотра и показать целевой репозиторий. Личная глобальная тема требует абсолютный разрешённый HTTPS-адрес фона: относительный путь без репозитория неоднозначен.
- [x] Для репозитория открывать редактор JSON в `OWNER/REPO`, для профиля в `USERNAME/USERNAME`, для организации в `ORG/.github`. Сначала искать `.bettergithub.json`, затем `bettergithub.json`, и редактировать существующий вариант без дубликата. Если обоих нет, создавать `.bettergithub.json`. Запасной поиск `OWNER/.github` у профиля остаётся для совместимости при чтении.
- [ ] Относительный фон `assets/background.png` разрешать от корня репозитория, где лежит найденный JSON, используя его `assetBase`: для профиля это `USERNAME/USERNAME/assets/background.png`, для организации `ORG/.github/assets/background.png`. При импорте сохранить контекст исходного репозитория для предпросмотра; при экспорте в другой репозиторий потребовать новый путь или абсолютный URL. Изображение пользователь загружает в репозиторий вручную. Отсутствующее изображение показывать как ошибку предпросмотра, не ломая страницу.
- [ ] Редактор GitHub сам проверяет права и правила ветки, а пользователь подтверждает коммит. Проверить передачу содержимого на живых авторизованных страницах Chromium и Firefox; кнопка копирования JSON уже есть как запасной вариант. Локальный предпросмотр остаётся только в браузере до коммита. Проверять цвета `#RRGGBB`, эффекты и URL по белому списку; не выполнять CSS/HTML/JS из JSON.

**Готово, когда:** экспортированный JSON после ручного размещения одинаково выглядит у посетителя без личной библиотеки; повреждённый импорт не меняет состояние; фон загружается из правильного репозитория.

## Этап 3. Единая модель редактора и экспорт

- [ ] Зафиксировать поддерживаемые поля: `appearance.theme`, `customTheme`, `accent`, `base`, `surface`, `text`, `muted`, `border`, `background`, `effect`; `banner`, `icon`, `installUrl`; `layout.sidebar` и позднее `layout.profile`. Использовать один формат для загрузки, предпросмотра, локального сохранения и экспорта.
- [ ] Разделить исходный публичный JSON, локальный черновик и итоговые значения для предпросмотра. Дать явные действия «Применить локально», «Сбросить черновик» и «Скачать .bettergithub.json»; отмена закрывает редактор без сохранения. При экспорте включать значения, которые пользователь видит в предпросмотре, включая выбранную личную тему, если она нужна в опубликованном файле.
- [ ] Добавить проверку перед экспортом и понятные сообщения об ошибках: допустимые темы/эффекты, цвета `#RRGGBB`, порядок только известных блоков, разрешённые адреса изображений и ссылки установки. Сериализовать только поддерживаемые поля, без внутренних ключей хранилища и данных других страниц.
- [x] Скачивание JSON через `Blob` и временный `objectURL` остаётся запасным вариантом. Публикация открывает целевой файл в веб-редакторе GitHub; расширение не хранит токен и не делает прямой коммит через API. GitHub получает файл только после подтверждения коммита пользователем.

**Готово, когда:** файл, скачанный для каждой из трёх типов страниц, валиден, соответствует предпросмотру и после ручного размещения применяется существующим загрузчиком; отменённые правки не появляются после перезагрузки.

## Этап 4. Управление блоками репозитория на странице

- [ ] Добавить явный режим «Редактировать страницу»; в нём показывать доступные для текущей страницы ручки перетаскивания и заметные области сброса. Начать с пяти блоков `about`, `releases`, `packages`, `contributors`, `languages` в боковой панели репозитория. Отсутствующие блоки не создавать и не предлагать как цели перетаскивания.
- [ ] Во время перетаскивания обновлять только черновик и предпросмотр; сохранять порядок в `layout.sidebar` лишь по явному действию. Сохранить управление ↑/↓ для клавиатуры и сенсорных устройств, добавить отмену и сброс порядка.
- [ ] Применять порядок устойчиво при переходах GitHub Turbo и изменении DOM; не перемещать нативные узлы в чужие контейнеры и не захватывать клики по ссылкам или кнопкам GitHub. При неподдерживаемой разметке скрывать ручки и оставлять страницу работоспособной.

**Готово, когда:** мышью, клавиатурой и касанием можно изменить порядок видимых блоков; перезагрузка восстанавливает сохранённый порядок; до сохранения отмена возвращает исходный вид; штатные действия GitHub работают.

## Этап 5. Карандаши, цвет и вход через профиль

- [ ] Показать карандаши только в режиме редактирования у поддерживаемых целей: общий фон/тема, баннер, значок репозитория или профиля, кнопка установки и блоки боковой панели. Карандаш открывает компактную панель с относящимися к цели полями, а не редактирование произвольной разметки GitHub.
- [ ] Для темы дать палитру `accent`, `base`, `surface`, `text`, `muted`, `border`. Встроенный выбор цвета с HEX-полем и ползунками готов; остаются кнопки рядом с выбранными элементами и предпросмотр изображений.
- [ ] Позиционировать панель в пределах окна, обеспечить фокус, подписи, Escape и закрытие кликом вне панели; соблюдать `prefers-reduced-motion` и доступный контраст элементов управления. Изменения сразу показывать на странице, но не сохранять автоматически.
- [ ] На собственном профиле добавить вход в BetterGitHub рядом со штатным «Edit profile», не заменяя кнопку и не перехватывая её действие. Подтверждать собственный профиль по текущему пользователю и наличию нативного управления. Если подтвердить нельзя, показывать обычный локальный редактор без обещания публичного изменения. Из редактора дать выбор: тема для всех страниц лично, для этой страницы лично или экспорт для публичного профиля.
- [ ] Показывать источник значений в предпросмотре. Приоритет для `appearance`: глобальный личный режим; иначе локальная сохранённая настройка страницы; затем опубликованный JSON; затем встроенная тема. Баннер, значок, ссылка установки и порядок остаются настройками страницы.

**Готово, когда:** каждая поддерживаемая цель открывает свои настройки, цвет меняется в предпросмотре рядом с целью, а закрытие/отмена не повреждает страницу и не сохраняет черновик.

## Этап 6. Карточки профиля после тем

- [x] Поддержать порядок видимых карточек профиля: README, Pinned, Contributions, а слева — профиль и контакты, Achievements, Highlights. В режиме редактирования дать каждой группе отдельную ручку из шести точек и область сброса; ссылки GitHub остаются кликабельными.
- [x] Хранить порядок в `profile.layout.profile` и `profile.layout.profileSidebar` опубликованного `USERNAME/USERNAME/.bettergithub.json` (существующий `bettergithub.json` тоже читается) и в `layout.profile`/`layout.profileSidebar` локальной настройки профиля. Старые JSON с порядком в корне читать для совместимости. Отсутствующие блоки не создавать, неизвестные ID игнорировать.
- [ ] Во время перетаскивания менять только черновик и предпросмотр. Клавиши ↑/↓ и отмена уже работают; добавить отдельный сброс и проверить GitHub Turbo и мобильный профиль вручную.

**Готово, когда:** README и Pinned меняются местами мышью и клавиатурой; отмена восстанавливает исходный порядок; локальное сохранение переживает перезагрузку; опубликованный профильный JSON задаёт тот же порядок другому посетителю; ссылки и штатные действия работают.

## Этап 7. Проверка и выпуск

- [ ] Добавить тесты на миграцию, выбор и приоритет тем, импорт/экспорт, фоновые пути, цветовые режимы, порядок репозитория и профиля, отмену, GitHub Turbo и повторное открытие редактора.
- [ ] Проверить вручную Chromium и Firefox: репозиторий, профиль, организация, светлая и тёмная темы, узкое окно, клавиатура, касание там, где доступно. Собрать оба пакета через `build.ps1` и выполнить `npm test`.
- [ ] Обновить `README.md` и `examples/.bettergithub.json`: короткая инструкция «редактировать → скачать → загрузить в корень нужного репозитория», перечень поддерживаемых элементов и ограничений.

**Готово, когда:** один и тот же экспорт воспроизводит оформление в обоих браузерах, проверенные действия GitHub не ломаются, а инструкции позволяют опубликовать конфигурацию без ручного редактирования JSON.

## Правила безопасности и совместимости

- Не исполнять CSS, HTML или JavaScript из JSON и не вставлять пользовательские строки как разметку. Для цветов и адресов использовать существующие ограничения `content.js`, объединённые с проверкой перед экспортом; изображения разрешать только с GitHub и допустимых относительных путей, ссылку установки — только на GitHub Releases по HTTPS.
- Сохранять размер публичного файла в пределах текущего лимита 64 КБ и совместимость с существующим форматом без обязательной миграции. Проверять, что экспорт не включает настройки иных репозиториев и личные данные из хранилища.
- Использовать общую логику редактора для Chromium MV3 и Firefox MV3; различия манифестов и сборки оставить в `manifest.chromium.json`, `manifest.firefox.json` и `build.ps1`.
